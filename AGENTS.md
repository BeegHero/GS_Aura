# Repository Guidelines

## Project Structure & Module Organization
- `Source/` contains the C++ game module (`Source/Aura`) with `Public/`, `Private/`, and `UI/` headers/sources.
- `Content/` holds Unreal assets (Blueprints, maps, materials, etc.).
- `Config/` stores engine and project settings (`DefaultEngine.ini`, `DefaultInput.ini`).
- `Platforms/`, `Binaries/`, `Intermediate/`, `Saved/`, and `DerivedDataCache/` are generated by Unreal; do not hand-edit.

## Build, Test, and Development Commands
- Open `Aura.uproject` in Unreal Editor to run the game and iterate on assets.
- Generate project files (right-click `Aura.uproject` in Explorer) to update the IDE solution.
- Build from your IDE using `Aura.sln` (Visual Studio) or via UnrealBuildTool as configured by your environment.

## Coding Style & Naming Conventions
- Follow Unreal C++ conventions found in `Source/Aura`: PascalCase types (`AAuraCharacter`), `U`/`A`/`F` prefixes, `b` prefix for bools, and `Get/Set` accessor names.
- Indentation is tabs in existing files; match the surrounding file style.
- Keep headers in `Public/` and implementation in `Private/` where possible.

## C++ vs Blueprint Responsibilities
- Put core gameplay logic, performance-critical systems, and networking authority rules in C++ (e.g., ability system components, attribute calculations).
- Use Blueprints for rapid iteration, visual scripting of interactions, and content assembly (e.g., UI widgets, level scripting, lightweight behavior).
- Expose C++ hooks to Blueprints with `BlueprintCallable`/`BlueprintImplementableEvent` and keep Blueprint graphs thin; avoid duplicating gameplay rules in both layers.

## Testing Guidelines
- No dedicated automated test suite is present. If you add tests, use Unreal Automation tests and place them under `Source/Aura/Private/Tests` (or similar).
- Name tests clearly by feature (e.g., `Aura.Inventory.AddItem`), and document how to run them in this file.

## Commit & Pull Request Guidelines
- Recent commits use short, lesson-style summaries (e.g., `Lesson 188`). There is no enforced convention.
- Prefer concise, imperative messages with a scope when possible (e.g., `AbilitySystem: fix attribute init`).
- PRs should include: a brief description, repro/verification steps, and screenshots or videos for UI/visual changes. Link related issues when applicable.

## Configuration & Assets
- Store project settings in `Config/` rather than hardcoding values.
- Keep new assets under relevant `Content/` subfolders (e.g., `Content/Blueprints/`, `Content/Maps/`).
